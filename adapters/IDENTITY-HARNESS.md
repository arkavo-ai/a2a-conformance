# Identity harness behavior contract (Phase 1)

How the `arkavo-ext-*` adapters realize `scenarios/arkavo/identity/*` against
`specs/arkavo/aia-identity-v1.md`. Supplements CONTRACT.md; the ops contract
is unchanged.

## Shared fixtures

`adapters/shared-fixtures/identity/` holds the committed P-256 test keys (see
its README) and `manifest.json`, generated by the Rust implementation's
fixture tool and cross-verified by Swift:

```jsonc
{
  "issuerDid": "did:key:zDn...",        // derived from test-issuer key
  "clientDid": "did:key:zDn...",        // derived from test-client-agent key
  "serverDid": "did:key:zDn...",        // derived from test-server-agent key
  "iss": "https://identity.arkavo.net", // spec-pinned issuer string
  "vectors": {
    "cwtValid": "<base64url COSE_Sign1>",       // aud = serverDid, 240s TTL from iatEpoch
    "cwtExpired": "<base64url COSE_Sign1>",     // exp in the past relative to iatEpoch
    "cwtWrongAudience": "<base64url COSE_Sign1>", // aud = did:key of a fourth, throwaway key
    "iatEpoch": 1750000000,                     // fixed epoch the static vectors were minted at
    "signedCard": { ... },                      // AgentCard with valid signatures[0], signed by serverDid
    "tamperedCard": { ... }                     // same card, one byte of description changed AFTER signing
  }
}
```

Static CWT vectors are for **unit-level cross-verification** (verify-at-fixed-
epoch: verifiers accept an injected `now` for these tests). Harnesses mint
**fresh** CWTs at runtime with the same keys — live scenarios never depend on
the fixed epoch.

## Scenario-keyed harness behavior

Server harness (`arkavo-ext-rust` / `arkavo-ext-swift`), on `/select`:

| scenario | server arming |
|---|---|
| `arkavo/identity/cwt-auth-success`, `cwt-expired`, `cwt-wrong-audience` | **auth required**: HTTP layer verifies Bearer CWT per spec (trust root = test-issuer pub, expected aud = own DID = serverDid, replay cache on). 401 with `WWW-Authenticate: Bearer error="invalid_token"` for missing/invalid/expired/**wrong-audience** credentials (RFC 6750: the token is not valid for use at this resource; spec §8). 403 is reserved for authenticated-but-unauthorized, which Phase 1 scenarios do not exercise. The scripted A2A handler behind it is the normal one. |
| `arkavo/identity/card-signature-valid` | serve `manifest.vectors.signedCard` with `{{baseUrl}}` substituted **before signing at /select time** (the harness re-signs after substitution so the signature covers the served bytes' canonical form). |
| `arkavo/identity/card-signature-tampered` | serve the re-signed card with one post-signing content mutation (flip one character of `description`). |
| every other scenario (incl. all core/ and arkavo/degradation/) | **auth NOT armed** — vanilla behavior; this is the degradation contract in action. |

Client harness, scenario-keyed credential selection:

| scenario | client behavior |
|---|---|
| `cwt-auth-success` | resolve card → read target DID from extension params (fallback: serverDid from manifest) → mint fresh CWT (test-client key, aud = target DID, iss per spec, TTL 240s) → present per spec §4 → run op |
| `cwt-expired` | mint CWT with `exp` 60s in the past → present → op. Expected: SDK surfaces transport-level auth failure → outcome `error`, `errorCode` null, `errorMessage` carrying the HTTP status |
| `cwt-wrong-audience` | mint fresh CWT with aud = throwaway DID → present → op. Expected: 401 `invalid_token` → outcome `error` |
| `card-signature-valid` | ResolveCard with verification ON (fail-closed mode: consumer requires identity) → outcome `card` on verified success |
| `card-signature-tampered` | same → verification fails → outcome `error` (spec §6: present-but-invalid fails closed) |
| every other scenario | no credentials attached (vanilla client path) |

Implementation note: scenario-keyed behavior lives in the **harness**, keyed
on the scenario id prefix — exactly like the tolgaki harness's loopback
seeding. SDK code paths must not know scenario ids.

## Matrix & CI

`arkavo-ext-rust` / `arkavo-ext-swift` wrap the same SDKs as the core
adapters plus the arkavo-a2a-* extension layers. Until the §7.5 licensing
decision, the extension repos are private, so:

- public CI builds and gates **core cells only** (explicit `--cell` lists);
- extension cells run locally / on self-hosted runners with repo access;
- their evidence is the committed `reports/baseline-ext.ndjson` + matrix
  snapshot, regenerated on every extension change.
